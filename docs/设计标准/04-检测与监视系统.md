# 检测与监视系统

## 1. 概述

检测系统提供三种检测能力（颜色/OCR/图片匹配），以及基于检测的持续监视机制。

## 2. 截图子系统

### 2.1 截图方式

| 方式 | 实现 | 性能 | 适用场景 |
|------|------|------|----------|
| DXGI | `CaptureManager` (Desktop Duplication API) | 高（~60fps） | 持续监视、高频检测 |
| BitBlt | `_capture_bitblt()` (Windows GDI) | 中 | 无截图源时的默认回退，DPI 缩放正确 |
| mss | `_capture_mss()` (跨平台截图库) | 中 | BitBlt 失败时的兜底 |

**截图回退链**：`capture_screen()` 自动按优先级选择：
1. 有截图源节点 → DXGI（小区域 <500×500 自动走 BitBlt）
2. 无截图源节点 → BitBlt
3. BitBlt 失败 → mss 兜底

### 2.2 截图源节点 (`detection/capture_source`)

控制 DXGI 后台截图的启停：

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enabled` | bool | true | 是否启用 DXGI |
| `fps` | number | 60 | 截图帧率 |
| `capture_mode` | string | fullscreen | fullscreen / region |
| `region` | region | [0,0,0,0] | 截图区域 |

## 2.5 坐标系统约定

所有检测节点和监视器统一使用三种坐标模式，通过 `mode` 参数控制：

| 模式 | 存储内容 | resolve_region 转换 | 适用场景 |
|------|---------|---------------------|---------|
| `screen` | 物理像素坐标（整数） | 直通 `int(x), int(y)` | 全屏模式 |
| `window` | 物理像素坐标（整数） | `cx + x, cy + y`（窗口客户区原点 + 存储值） | 窗口模式 |
| `relative` | 0~1 归一化比例 | `cx + x*cw, cy + y*ch` | 跨分辨率适配 |

**坐标全链路**：
```
拾取器(tools.js)  → px → 直接存储物理坐标 → 写入属性
属性面板(renderers.js) → 原样显示物理坐标
后端(coordinate.py) → resolve_region: 存储值 + 窗口原点 → 物理坐标 → capture_screen
```

**关键约定**：
- `screen` 模式：前端存储物理像素坐标（所见即所得），属性面板原样显示，后端执行时 `int(x), int(y)` 直通
- `window` 模式：前端存储物理像素坐标（与 screen 模式一致），属性面板原样显示，后端运行时加窗口客户区原点偏移。**2026-05 重构**：从「逻辑坐标」改为「物理坐标」存储，消除 DPI 双向转换的复杂性
- `relative` 模式：前端存储 0~1 比例值，属性面板原样显示比例值（如 0.5, 0.3），后端运行时 `cx + x*cw, cy + y*ch`
- 所有检测/监视节点的 `rect`/`region` 参数标记 `coordMode: true`，自动获得坐标拾取/框选按钮并归入「坐标」分组
- `hwnd_var` 参数标记 `varRef: true`，引擎自动解析 `${变量}` 引用

### 4.2 文字监视器 (`monitor/monitor_ocr`)

参数与颜色监视器类似，额外支持 OCR 特有参数。

### 4.3 OCR 缓存策略

OCR 是昂贵操作（50~200ms），需要缓存策略减少不必要的调用：

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| `disabled` | 每次都 OCR | 文字频繁变化 |
| `time_interval` | N ms 内复用上次结果 | 文字变化不频繁 |
| `frame_diff` | 画面无变化则跳过 OCR | 静态画面（推荐） |

**帧差缓存原理**：
1. 截图后与上次截图做 numpy 像素差异比较
2. 差异小于阈值 → 画面没变 → 复用上次 OCR 结果
3. 差异大于阈值 → 画面变了 → 执行 OCR
4. 帧差比较耗时微秒级，远小于 OCR 的 50~200ms

## 5. 图片匹配（模板匹配）

### 5.1 检测节点 (`detection/check_image`)

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `mode` | enum | screen | screen / window / relative |
| `rect` | region | [0,0,0,0] | 搜索区域（0=全屏） |
| `template_path` | string | "" | 模板图片路径 |
| `method` | enum | tm_ccoeff_normed | 匹配算法 |
| `threshold` | number | 0.8 | 匹配阈值（0~1） |
| `multi_match` | bool | false | 多目标匹配 |
| `pyramid_levels` | number | 2 | 金字塔加速层级 |
| `wait` | bool | false | 是否等待模式 |
| `wait_interval_ms` | number | 16 | 等待轮询间隔 |
| `wait_timeout_ms` | number | 5000 | 等待超时 |
| `store_var` | string | "" | 存储匹配坐标到变量 |

输出端口：`match` / `no`

### 5.2 匹配算法

| 算法 | 说明 |
|------|------|
| `tm_ccoeff_normed` | 归一化相关系数匹配（推荐，抗光照变化） |
| `tm_ccorr_normed` | 归一化互相关匹配 |
| `tm_sqdiff_normed` | 归一化平方差匹配 |

### 5.3 金字塔加速

大图搜索时自动启用金字塔加速：
1. 将原图和模板逐级缩小（pyrDown）
2. 在最小层级做粗匹配
3. 在粗匹配位置附近做精匹配
4. 大幅减少计算量

触发条件：图片 > 500×500 且模板 > 50×50

### 5.4 多目标匹配

`multi_match=true` 时返回最多 10 个匹配点，存入变量为数组格式。

### 5.5 帧差缓存

图片匹配也是昂贵操作，已实现帧差缓存（7期）：
- 原理同 OCR 帧差缓存（§4.3）
- 画面无变化时跳过模板匹配
- 适用于监视器轮询场景
- 通过 `do_image_match()` 的可选参数 `cache_strategy` / `cache_interval_ms` / `cache_key` 控制

## 6. 监视器通用机制

### 6.1 执行模型

```
[监视器启动] → poll_loop 线程（后台轮询）
                  ↓ 检测到目标
              trigger_signal.set()
                  ↓
              主线程执行 trigger 端口下游
                  ↓ 下游执行完毕
              flow_done.set()
                  ↓
              poll_loop 继续（如果 auto_stop=false）
```

### 6.2 循环触发模式 (`auto_stop=false`)

- 触发后不停止，等待 `recheck_delay_ms` 后继续检测
- 每次触发只等待**单个下游节点**执行完毕（`flow_done.wait()`），然后继续
- 受 `max_triggers` 和 `auto_close_after_ms` 限制

### 6.3 `on_trigger` 行为

| 值 | 行为 |
|------|------|
| `branch` | 执行 trigger 端口下游（默认） |
| `stop_all` | 全局停止 |
| `stop_task` | 停止指定异步任务 |
| `pause_task` | 暂停指定异步任务 |
| `resume_task` | 恢复指定异步任务 |

### 6.4 触发模式 (`trigger_mode`)

| 值 | 行为 |
|------|------|
| `appear` | 目标出现时触发 |
| `disappear` | 目标从有到无（消失）时触发 |
| `change` | 目标状态变化时触发 |
| `absent` | 目标不存在时触发（7期新增）。与 disappear 区别：absent **不要求**先检测到目标再消失，只要当前帧未检测到目标就触发 |

### 6.5 初始检查模式 (`initial_check`) — 7期新增

控制监视器启动后**第一帧**的检测行为，仅对 `disappear` 和 `change` 模式生效：

| 值 | 行为 |
|------|------|
| `baseline` | 第一帧仅记录基线状态，不触发。后续帧状态变化时才触发（默认，向后兼容） |
| `trigger` | 第一帧即参与触发判定。如 disappear 模式下第一帧就未检测到目标 → 立即触发 |

`absent` 模式不受 `initial_check` 影响——absent 语义本身就是"当前未检测到即触发"，无需基线对比。

## 8. 时间监视器 (`monitor/monitor_time`)

### 8.1 参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `hour` | number | 8 | 目标小时(0-23) |
| `minute` | number | 0 | 目标分钟(0-59) |
| `second` | number | 0 | 目标秒(0-59) |
| `next_day` | bool | false | 若已过目标时间的行为（见下文） |
| `check_interval` | number | 500 | 检查间隔(ms) |
| `timeout` | number | 0 | 超时(ms, 0=无限) |
| `on_trigger` | enum | branch | 触发后行为 |
| `auto_stop` | bool | true | 触发后自动停止 |
| `max_triggers` | number | 0 | 最大触发次数(0=无限) |
| `recheck_delay_ms` | number | 500 | 循环模式重检间隔 |
| `auto_close_after_ms` | number | 0 | 自动关闭超时 |

### 8.2 `next_day` 参数语义

`next_day` 控制当目标时间已过时监视器的行为：

| next_day | 时间已过时行为 | 典型场景 |
|----------|-------------|---------|
| **否** | 立即触发一次，然后等待次日同一时间 | "每天8点执行，如果启动时已过8点则立即补执行一次" |
| **是** | 不触发，直接等待次日同一时间 | "每天8点执行，错过了就等明天" |

### 8.3 与 `max_triggers` 的组合行为

| next_day | 时间状态 | max_triggers | 实际行为 |
|----------|---------|-------------|---------|
| 否 | 已过 | 1 | 立即触发1次 → 关闭 |
| 否 | 已过 | 2 | 立即触发1次 → 等次日 → 触发第2次 → 关闭 |
| 否 | 已过 | 0(无限) | 立即触发1次 → 每天循环触发 |
| 否 | 未到 | 任意 | 等到目标时间 → 按max_triggers循环 |
| 是 | 已过 | 任意 | 等到次日 → 按max_triggers循环 |
| 是 | 未到 | 任意 | 等到目标时间 → 按max_triggers循环 |

### 8.4 timeout 分支

timeout 分支仅在以下情况触发：
- 监视器设置了 `timeout > 0`，且在目标时间到达前超时
- 监视器设置了 `auto_close_after_ms`，自动关闭超时

**注意**：目标时间已过且 `next_day=False` 时走 **trigger** 分支（立即触发），**不是** timeout 分支。

## 9. 预设节点

### 9.1 `preset/preset_click`（预设点击）

移动到坐标并点击。封装了坐标解析 + 移动 + 点击的常用组合。

### 9.2 `preset/preset_find_click`（找图点击）

找图并点击。封装了截图 + 模板匹配 + 点击的常用组合。
实现上复用 `check_image` 的匹配逻辑（`do_image_match()`），避免两套模板匹配实现。
支持 `store_var` 参数将匹配坐标存入变量（7期新增），与 `check_image` 行为一致。

### 9.3 `preset/preset_read_text`（读取文字）

OCR 读取文字并存储到变量。封装了截图 + OCR + 变量存储的常用组合。
