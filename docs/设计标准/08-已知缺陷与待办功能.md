## 1. 已知缺陷 (Bug)

### 1.1 goto 在分支内静默失效

**严重程度**：高

**现象**：在 Fork/Race 分支内使用 `control/goto` 节点时，跳转不生效。

**根因**：
- `_handle_goto` 设置的是 `ctx._goto_target`（全局上下文）
- `_execute_node` 读取的是 `branch_ctx._goto_target`（分支上下文）
- 分支内 `branch_ctx._goto_target` 为 None，goto 静默失效

**影响范围**：所有在 Fork/Race 分支内使用 goto 的场景。

**状态**：✅ **已修复 (6期)** — 修改 engine.py 读取逻辑，优先检查 branch_ctx._goto_target，为空时回退到 ctx._goto_target。

### 1.2 goto 跨分支跳转

**严重程度**：中

**现象**：无法从一个分支跳转到另一个分支的节点。

**状态**：如无法实现跨分组跳转，作为 bug 记录。待确认。

### 1.3 监视器分支中 goto 的编译期警告

**严重程度**：低（8期新增）

**现象**：监视器节点的触发分支中使用 `control/goto` 时，编译期产生警告但不阻止执行。

**根因**：监视器运行在独立线程中，goto 的跳转目标在主流程中。goto 在监视器分支中的语义不明确——可能工作（如果 `_goto_target` 被正确传递），也可能不工作。

**当前行为**：8期修复后，编译期会对监视器分支中的 goto 产生警告，但允许执行。用户可自行评估风险。

**状态**：✅ **已修复 (8期)** — 在 `parse_graph` 中调用 `_check_goto_in_flow`，改为警告而非错误。

### 1.4 check_results 并发访问安全性

**严重程度**：低（8期确认，后期修复）

**现象**：Fork 并发分支同时操作 `check_results` 字典时，理论上可能触发 `RuntimeError: dictionary changed size during iteration`。

**评估**：
- Python GIL 提供基本保护，但**不保护**字典遍历期间的修改
- 实际触发概率极低（需两个分支在同一微秒级窗口内操作同一字典）
- 加锁会增加每次访问的开销，影响执行精度

**状态**：⏳ **后期考虑** — 当前作为可接受风险，如用户报告此崩溃则优先修复。

### 1.5 _detect_cycle_dfs visited 集合行为

**严重程度**：低（8期确认，后期修复）

**现象**：`_check_fork_join_cycles` 中 `_detect_cycle_dfs` 的 `visited` 集合在递归返回后不清除，导致后续环检测可能跳过部分路径。

**评估**：可能是有意设计（已确认安全的节点不重复检查）；漏检场景极罕见。

**状态**：⏳ **后期考虑**

## 2. 待办功能

### 2.1 图片匹配帧差缓存

**优先级**：高 ✅ **已实现 (7期)**

**描述**：为 `detection/check_image` 节点和 `preset/preset_find_click` 添加帧差缓存策略，与 OCR 的帧差缓存机制一致。

已通过给 `do_image_match()` 添加可选 `cache_strategy`/`cache_interval_ms`/`cache_key` 参数实现，复用 `ctx.last_capture_cache` 和 `ctx._image_match_cache`。

### 2.2 编译缓存 ✅ **已实现 (7期)**

**优先级**：高

**描述**：为旧格式宏脚本（`.json`）添加编译缓存，避免同一宏被循环调用时重复编译。已通过 `_script_compile_cache` 字典实现（`handlers/control.py`），key 为 `(path, os.path.getmtime(path))`，生命周期一次执行期间。缓存开关受图设置 `script_compile_cache` 控制（默认 `true`），`call_script_sync/async` 均生效。

> **附注**：设计标准中此条目原标记为"待办"，经代码审查确认已完整实现。

### 2.3 轮询间隔可配置

**优先级**：中 ✅ **已实现 (7期)**

**描述**：`wait_cond`、`seq_check`、`state_machine` 节点的轮询间隔（当前硬编码 100ms）改为节点参数，允许用户自定义。

前后端均已添加 `poll_interval_ms` 参数（默认 100ms，支持 varRef）。handler 读取该参数替代硬编码值。

### 2.4 preset_find_click 复用 check_image 逻辑

**优先级**：中 ✅ **已实现 (7期)**

**描述**：`preset/preset_find_click` 当前独立实现了模板匹配逻辑，已改为调用 `do_image_match` 公共函数（`handlers/detection.py`），`check_image` 和内联 `_do_check_image` 也共用该函数。帧差缓存统一在 `do_image_match` 中实现。

## 3. 搁置项（后期待确认）

### 3.1 监视器停止机制

**描述**：监视器触发后，是否需要一个显式的"停止监视器"节点，还是仅靠 `auto_stop` 参数和 `max_triggers` 控制。

**当前行为**：
- `auto_stop=true`：触发后自动停止
- `auto_stop=false`：持续触发，受 `max_triggers` 和 `auto_close_after_ms` 限制
- 无显式停止节点

**待确认**：是否需要新增 `control/stop_monitor` 节点。

## 4. 非必须项（已确认不做）

| 议题 | 描述 | 决定 |
|------|------|------|
| if_else 无条件连接警告 | 编译期警告用户未连接条件 | 不做 |
| Join 超时独立端口 | 超时后走 timeout 端口而非 done | 不做 |
| 分支局部变量 | 变量按分支隔离 | 不做（全局共享更简单） |
| 新引擎独立参数 section | 新增 executor_new section | 不做（复用旧引擎参数） |
| 监视器暂停/恢复 | 监视器后台轮询线程不响应暂停信号 | 不做（监视器模型不允许暂停恢复） |
| 动态变量名 | `var_set` 的 name 字段支持变量引用 | 不做（用户若需动态命名，再使用一次设置变量节点） |
| flow 分类颜色统一 | 流程分类颜色与 flow/start 节点颜色不一致 | 不做（起始/结束节点颜色特殊化是有意设计，强调其特殊性） |
| 工具节点隐式变量消除 | 9个工具运算节点自动创建 `_out` 隐式变量 | 不做（特性：用户若需改名，再使用一次设置变量节点） |
| 坐标模式画布内联编辑 | `_pickSummaryKeys` 中 mode 被 skip | 不做（坐标模式与坐标捕获器联动，单独修改坐标模式意义不大） |
| 前端校验 flow/end | validateGraph 不检查 flow/end 节点 | 不做（用户可以不配置 end 节点） |

## 5. 设计意图说明（非缺陷）

以下行为是设计意图，非缺陷：

| 行为 | 说明 |
|------|------|
| `flow/end` 全局终止 | 设计意图：任何分支到达结束节点 = 任务完成。如仅需结束当前分支，使用 `control/stop_branch` |
| Fork `done` 端口 | 简单场景自动汇合，复杂场景用 Join |
| Race 分支自然结束 = 胜出 | 不需要 `race_win` 也能胜出 |
| `call_script_sync` ≤2 步短路径 | 有意优化，跳过旧引擎开销 |
| `var_compare` 自动类型推断 | 先数字比较，失败则字符串比较 |
| 变量全局共享 | 用户自行管理命名，避免并发冲突 |
| 书签坐标实时解析 | window/relative 模式每次查询窗口位置 |
| 监视器不响应暂停 | 监视器后台轮询线程不暂停；延迟/等待节点暂停后恢复时跳过剩余等待时间 |
| 起始/结束节点颜色特殊化 | flow 分类颜色与 flow/start/flow/end 节点颜色不同，强调起始/结束节点的特殊性 |
| 工具节点隐式 `_out` 变量 | 常量/运算节点自动创建 `{id}_out` 变量存储结果，方便下游引用 |
| 复制粘贴仅保留内部连线 | 粘贴节点时仅保留被复制节点之间的连线，连到外部节点的连线不保留 |
| `store_var` 等输出变量标记 `varRef` | 输出变量字段（`store_var`、`store_number`、`counter_var` 等）标记 `varRef: true`，允许用户通过 `$` 按钮选择已有变量进行覆盖。这是设计意图：用户可能需要动态选择要覆盖的变量名，或使用 `${动态变量名}` 实现运行时决定存储目标 |
| `goto` 节点仅使用 `varRef`，不使用 `nodeRef` | goto 的目标节点通过变量引用（`varRef`）动态指定，而非 dropdown 选择器（`nodeRef`）。理由：goto 的目标通常由运行时逻辑决定（如循环跳回、条件分支），固定下拉选择意义不大。`join` 和监视器使用 `nodeRef` 是因为它们的关联目标在设计期确定 |
| 监视器 `absent` 触发模式 | `absent` 模式（7期新增）不要求先检测到目标再判定"消失"，只要当前帧未检测到目标即触发。与 `disappear`（从有到无）语义不同，适用于"确保某色块/文字不出现"的场景 |

## 6. 暂停行为设计规范

### 6.1 暂停响应范围

| 组件 | 是否响应暂停 | 行为 |
|------|-------------|------|
| 延迟节点 (`utility/wait`) | 是 | 暂停期间倒计时继续；恢复后若延迟已过期则立即完成 |
| 检测节点 wait 轮询 | 是 | 暂停期间冻结轮询；恢复后继续等待 |
| 控制节点轮询 (`wait_cond`/`seq_check`/`state_machine`) | 是 | 暂停期间冻结轮询；恢复后继续等待 |
| 同步宏短路径 | 是 | 与长路径行为一致 |
| 监视器后台线程 | 否 | 监视器模型不允许暂停恢复，轮询继续运行 |

### 6.2 延迟/等待暂停恢复语义

暂停期间底层计时器不停止。恢复后：
- 若剩余等待时间已耗尽 → 立即完成当前等待
- 若剩余等待时间未耗尽 → 继续等待剩余时间

这避免了暂停期间累积延迟，确保脚本行为可预测。
