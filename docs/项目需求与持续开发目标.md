# 项目需求与持续开发目标

> 本文档基于对代码库与既有文档的通读 + 运行时实测，确认 **MacroDriver WebUI** 的项目定位、
> 目标场景、当前能力边界与后续开发路线。
> 文中所有结论均带 `文件:行号` 依据，性能数字为本机实测（1920×1080 主屏 + 副屏，Python 3.13.14）。

---

## 一、项目定位

一款 **Windows 本地高精度宏驱动控制台**（Python + pywebview），两大核心能力：

1. **宏录制 / 编辑 / 精确执行** —— 微秒级时序的键鼠回放
2. **自动化流程可视化编辑与执行** —— 拖拽式节点图，支持 Fork/Join/Race 并发、图像/颜色/OCR 检测

关键差异化：**双输入驱动**（SendInput 兼容 + Interception 内核级注入）+ **native standby 引擎**
（C 扩展，绕过 Python/GIL 直接消费预编译 QPC 时间线）+ **PI/前馈延时补偿**。

---

## 二、目标场景与由此推导的硬性需求

### 场景
针对《原神》设计一串自动化流程，用**高精度宏执行 + 及时图像识别**完成自动化战斗。

### 推导出的四条硬性需求（彼此存在张力，是本项目的核心设计约束）

| # | 需求 | 量化目标 | 现状（修复前） | 现状（本轮修复后） |
|---|------|---------|--------------|------------------|
| R1 | **节点间低延迟** | 单次检测 ≤ 10ms，节点派发 ≤ 10µs | 派发 30~150µs；全屏检测 21~114ms；Fork+Join 闭环 ≥100ms | 派发 3.9µs（与图规模解耦）；一次循环迭代 5 个检测节点 91.3ms → **15.9ms** |
| R2 | **检测结果实时（不能陈旧）** | 检测结果 = 当前帧 | 默认 100ms 陈旧缓存，跨循环迭代**永不失效** | 默认改为 `disabled`；循环迭代强制失效；共享帧缓存上限 4ms |
| R3 | **不抢占游戏 CPU** | 进程优先级通常不高于游戏，受用户延迟选择影响；绑核隔离 | 进程被抬到 HIGH/REALTIME_PRIORITY_CLASS 且**永不恢复** | 改为可按档位设置 + 可恢复；精度靠核隔离而非高优先级 |
| R4 | **提供多种精度档位** | 一个入口联动一组参数 | 25+ 个平铺开关，无统一入口，存在互斥组合 | 新增 4 档位（延迟优先/均衡/低占用/自定义），一键联动 15 项参数 |

> **R1 与 R3 是本项目的根本张力**：降低延迟的传统手段（提高优先级、忙等自旋、提高系统定时器分辨率）
> 恰恰都会抢走游戏的 CPU。本项目的解法是 **用核隔离（binding）而非优先级** 换精度 ——
> 把宏线程钉在末尾核心上，其余核心留给游戏；native standby 引擎单核自旋同理。

## 三、架构现状（审查结论）

### 3.1 执行模型

```
execute_graph() → _drive_with_goto_trampoline()   ← 顶层 trampoline（本轮新增）
  └─ _execute_node()  ← 单线程 + goto 原地循环
       └─ handler() → _execute_flow() → _execute_node()   ← 递归派发
```

- **没有调度器/节点队列/tick**，靠 Python 递归推进，每节点约 2~3 个栈帧
- 并发靠线程派生：Fork 分支线程、Race 分支线程、监视器 poll 线程、异步宏 TaskPool worker
- 理论最小节点间延迟 **≈ 3.9 µs**（空图），本轮已使延迟与图规模解耦

### 3.2 主要技术债（按影响排序）

| 类别 | 问题 | 状态 |
|------|------|------|
| **实时性** | `_execute_flow` 每次转移 O(M) 全量扫 `check_results`（且结果无人消费） | ✅ 已删 |
| **实时性** | 检测缓存默认 100ms 陈旧值且跨迭代不失效 | ✅ 已改默认 + 循环失效 |
| **实时性** | 一次循环迭代 N 个检测节点 = N 次独立截图 | ✅ 共享帧缓存 |
| **可靠性** | `goto` 循环只能执行一圈；且栈随圈数增长 → RecursionError | ✅ 信号解栈 + trampoline |
| **资源** | 进程优先级提升后永不恢复 | ✅ 档位化 + 恢复 |
| **可靠性** | DXGI 属性名写错 → 硬件采集 100% 不可用，静默回退 BitBlt | ✅ 已修 |
| **契约** | 前端调 `get_node_defs`，后端只有 `get_node_definitions` | ✅ 已修 |
| **数据** | 保存对话框返回值取 `result[0]` → 导出路径变成单个字符 | ✅ 已修 |
| **数据** | 配置非原子写 + 损坏时静默被默认值覆盖 | ✅ 原子写 + 隔离备份 |
| **可用性** | F8 三方冲突 / F7、F10 双方冲突，且无冲突检测 | ✅ 已加检测 API |
| **资源** | 中止后普通键与鼠标中键卡死 | ✅ 已加按下跟踪与补发 |
| **正确性** | `move_to` 从屏幕原点 (0,0) 插值 → 视角瞬移 | ✅ 改为从当前光标插值 |

### 3.3 仍未解决（下一阶段重点）

## 六、开发约束（务必遵守）

1. **延迟与占用是一对矛盾，任何"提精度"的改动必须说明 CPU 代价。**
   优先用核隔离 / 减少重复工作，而不是提高优先级。
2. **禁止新增 `except: pass`。** 历史遗留的 70 处是"隐藏 bug"的主要载体。
3. **检测结果的默认语义必须是"当前帧"。** 任何缓存都必须可被循环迭代失效。
4. **图规模不得影响单节点延迟。** 新增热路径逻辑避免 O(M) 扫描。
5. **新增全局热键必须登记到 `HOTKEY_KEYS`**（`bridge/params_api.py`）以参与冲突检测。
6. **前后端契约改动必须双向核对**：前端 `window.pywebview.api.<name>` 与 bridge 方法名。

# 1. 引擎与检测回归测试
python -m automation.tests.test_engine_realtime

# 2. 编译全部自动化脚本
python -c "..."   # 见 automation/tests/
