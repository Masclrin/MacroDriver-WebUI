# MacroDriver WebUI 使用说明书

## 欢迎使用 MacroDriver

MacroDriver 是一款**可视化节点编辑器**，让你像搭积木一样搭建自动化流程。不需要写代码，拖拽节点、连线，就能让电脑自动帮你完成重复操作。

**典型用途**：

- 游戏中自动打怪、自动吃药、自动采集
- 检测屏幕上的文字/图片/颜色，自动做出反应
- 定时执行重复操作
- 同时做多件事（一边监视血量，一边自动攻击）

***

## 一、快速入门

### 1.1 界面概览

打开 MacroDriver 对应自动化编辑页后，你会看到：

```
┌──────────┐  ┌──────────────────────────────┐  ┌────────────┐
│ 节点面板  │  │                              │  │  属性面板   │
│ (左侧)   │  │         画布 (中间)            │  │  (右侧)    │
│          │  │                              │  │            │
│ 搜索框    │  │   [开始] → [节点] → [节点]     │  │  参数编辑   │
│ 节点列表  │  │                              │  │            │
│          │  │                              │  │            │
└──────────┘  └──────────────────────────────┘  └────────────┘
```

- **左侧**：节点面板，所有可用的节点都在这里，按分类排列
- **中间**：画布，你在这里搭建流程
- **右侧**：属性面板，选中节点后在这里修改参数

### 1.2 创建第一个自动化

1. 点击工具栏的 **新建** 按钮
2. 画布上会出现一个 **开始** 节点——所有流程从这里出发
3. 从左侧拖一个节点到画布上（比如"鼠标点击"）
4. 从开始节点的输出端口拖一条线到鼠标点击节点的输入端口
5. 选中鼠标点击节点，在右侧设置点击坐标
6. 点击工具栏的 **运行** 按钮

就这么简单！

### 1.3 基本操作

| 你想做什么 | 怎么做                |
| ----- | ------------------ |
| 添加节点  | 从左侧拖到画布上           |
| 移动节点  | 拖住节点标题栏            |
| 连接节点  | 从一个节点的圆点拖到另一个节点的圆点 |
| 删除节点  | 选中后按 Delete 键      |
| 修改参数  | 选中节点，在右侧修改         |
| 缩放画布  | 滚动鼠标滚轮             |
| 平移画布  | 按住鼠标中键拖动；按住空格键拖动   |
| 搜索节点  | 在左侧搜索框输入（支持拼音！）    |

## 二、核心概念

### 2.1 节点是什么？

节点就是一个"动作"或"判断"。每个节点有：

- **输入端口**（左侧圆点）：接收信号，触发节点执行
- **输出端口**（右侧圆点）：执行完后，把信号传给下一个节点
- **参数**：控制节点具体做什么（比如点击哪里、等多久）

### 2.2 两种连线

| 连线类型     | 颜色   | 用途     | 例子               |
| -------- | ---- | ------ | ---------------- |
| **流程连线** | 蓝色实线 | 控制执行顺序 | "做完A之后做B"        |
| **数据连线** | 绿色虚线 | 传递检测结果 | "把颜色检测的结果告诉条件判断" |

> **简单理解**：流程连线 = 先做什么后做什么；数据连线 = 把结果告诉谁。

### 2.3 开始和结束

- **开始节点**：每个自动化有且只有一个，是执行的起点
- **结束节点**：一旦执行到结束节点，**整个自动化全部停止**（包括所有正在同时运行的分支）

> ⚠️ **重要**：结束节点是"全局核爆"——不管你有多少分支在跑，碰到结束节点全部停掉。如果你只想结束当前分支，不要放结束节点，让分支自然跑完就行。

## 三、节点详解

### 3.1 动作类节点（绿色）

#### 鼠标点击

在指定位置点击鼠标。

| 参数    | 说明                                                                         |
| ----- | -------------------------------------------------------------------------- |
| 坐标模式  | **屏幕坐标**：相对于整个屏幕左上角；**窗口坐标**：相对于目标窗口左上角；**相对坐标**：相对于窗口客户区；**当前位置**：鼠标在哪就点哪 |
| X / Y | 点击坐标                                                                       |
| 按钮    | 左键 / 右键 / 中键                                                               |
| 点击类型  | 单击 / 双击 / 长按 / 按下不放 / 释放                                                   |
| 移动时长  | 鼠标移动到目标位置花多长时间（毫秒），0 = 瞬间移动                                                |

> **提示**：窗口坐标和相对坐标会自动跟随窗口移动——你把窗口拖到别的地方，坐标也会跟着变。

#### 按键动作

模拟键盘按键。

| 参数 | 说明                    |
| -- | --------------------- |
| 按键 | 要按的键（支持组合键如 Ctrl+C）   |
| 动作 | 按下 / 释放 / 打字（按下后自动释放） |

#### 文本输入

逐字符输入一段文字（比按键动作更适合输入中文）。

#### 鼠标滚轮

滚动鼠标滚轮（120是windows默认的一个滚动单位）。

#### 窗口管理

查找并操作窗口（激活、最小化、最大化等）。

***

### 3.2 检测类节点（绿色）

#### 颜色检测

检查屏幕上某个区域是否出现了指定颜色。

| 参数   | 说明                                                   |
| ---- | ---------------------------------------------------- |
| 目标颜色 | 要检测的颜色                                               |
| 容差   | 允许的颜色偏差（0=完全匹配，越大越宽松）                                |
| 检测模式 | **包含**：区域内是否有该颜色；**变化**：颜色是否发生了变化；**面积**：该颜色占比是否超过阈值 |

输出端口：

- **匹配**：检测到了 → 走这条线
- **不匹配**：没检测到 → 走这条线

#### 文字检测 (OCR)

识别屏幕上的文字。

| 参数   | 说明                                                                |
| ---- | ----------------------------------------------------------------- |
| 匹配文字 | 要匹配的文字内容                                                          |
| 匹配模式 | **包含**：文字中包含即可；**精确**：完全一致；**正则**：用正则表达式匹配；**数字大于/小于/等于**：识别数字后比较 |
| 缓存策略 | **关闭**：每次都识别；**时间间隔**：N毫秒内复用结果；**画面差异**：画面没变就跳过识别                 |

> **提示**：OCR 比较慢（50\~200ms），建议开启缓存策略。画面差异模式最智能——画面没变化就不重复识别。

#### 图片匹配

在屏幕上找一张图片（模板匹配）。

| 参数       | 说明                                                |
| -------- | ------------------------------------------------- |
| 模板路径     | 要查找的图片文件                                          |
| 阈值       | 匹配度要求（0\~1，0.8 = 80%相似即可）                         |
| 多目标      | 是否找出所有匹配位置                                        |
| 缓存策略     | **关闭**：每次都匹配；**时间间隔**：N毫秒内复用结果；**画面差异**：画面没变就跳过匹配 |
| 缓存间隔(ms) | 时间间隔模式下的复用时长，默认100ms                              |

> **提示**：
>
> - 大图搜索会自动启用金字塔加速，不用手动设置。
> - 开启缓存策略可以显著提升性能——画面没变化时直接复用上次结果，避免重复的模板匹配计算。
> - **画面差异模式最智能**：自动比较前后截图的像素差异，差异小就跳过匹配。适合检测静态UI元素。
> - 找图点击节点现在也复用了图像匹配的核心逻辑，保持一致性。

### 3.3 监视器节点（橙色）

监视器和检测节点的区别：**检测节点只检查一次，监视器会持续盯着**。

#### 颜色监视器 / 文字监视器

持续监视屏幕，一旦满足条件就触发动作。

| 参数     | 说明                                           |
| ------ | -------------------------------------------- |
| 检测间隔   | 多久检查一次（毫秒）                                   |
| 触发模式   | **出现**：目标出现时触发；**消失**：目标消失时触发；**变化**：目标变化时触发 |
| 自动停止   | 开启：触发一次就停；关闭：持续触发                            |
| 最大触发次数 | 触发多少次后自动停止（0=无限）                             |

> **重要**：当自动停止关闭时，监视器触发后会等你连在 trigger 端口后面的节点执行完，然后继续监视。每次只等一个下游节点。
>
> ⚠️ **注意**：`auto_stop=false` 模式适用于简单的循环触发场景（如定时执行某操作）。如果需要更复杂的循环逻辑（如每次触发后根据条件决定是否继续），建议改用 `loop_while` + 监视器节点的组合，这样更可控。

#### 定时监视器

按固定时间间隔触发，不检测任何东西。

***

### 3.4 控制类节点（紫色）

#### 条件判断 (if\_else)

根据条件走不同的分支。

- 输入端口 `cond` 接收数据连线（来自检测节点）
- 条件为真 → 走 **true** 端口
- 条件为假 → 走 **false** 端口

> **提示**：如果你没连条件数据线，节点会使用"默认结果"参数（默认走 false）。这不是 bug，是设计如此——简单场景不需要连数据线。

#### 等待

| 类型     | 说明                     |
| ------ | ---------------------- |
| 固定时长   | 等待指定时间（支持秒/分钟/毫秒）      |
| 等到指定时间 | 等到几点几分几秒（如等到 14:30:00） |

#### 等待条件 (wait\_cond)

反复检测上游条件，直到条件为真才继续执行。超时则走超时分支。

**画布连接方式：**

```
[检测节点] ──result(bool)──→ [wait_cond].cond(data_bool)
                                   │
                              ├─ met(通过)──→ 后续操作
                              └─ timeout(超时)──→ 超时处理
```

| 参数       | 说明                  | 示例               |
| -------- | ------------------- | ---------------- |
| 超时(ms)   | 最长等待时间，超时走timeout分支 | `10000` = 10秒    |
| 检查间隔(ms) | 每次检查之间的间隔           | `100` = 每0.1秒查一次 |

> **典型用途**：等游戏加载完成、等窗口出现、等某个UI元素显示出来。

#### 计数循环

重复执行 N 次。

#### 条件循环

只要条件满足就一直循环。

#### 顺序检测 (seq\_check)

**等待多个条件全部满足后才放行**，类似"门闸"——所有人都到齐才开门。

与 wait\_cond 的区别：wait\_cond 只等一个条件；seq\_check 等多个条件**同时**为真。

**画布连接方式：**

```
[检测A] ──result(bool)──┐
[检测B] ──result(bool)──┼──→ [seq_check].cond(data_bool)
[检测C] ──result(bool)──┘         │
                            ├─ pass(全通过)──→ 后续操作
                            └─ fail(失败/超时)──→ 处理
```

| 参数       | 说明                  | 示例                        |
| -------- | ------------------- | ------------------------- |
| 失败重试     | 是否重复检测。关闭=只测一次就放弃   | 默认开启                      |
| 最大重试次数   | 达到次数后走fail分支        | `100` = 最多等10秒（默认间隔100ms） |
| 轮询间隔(ms) | 每次检测之间的等待时间，默认100ms | `50` = 更快响应但更耗CPU         |

> **典型用途**：等游戏加载完成（需同时确认：按钮出现+加载条消失+血量正常）。

#### 状态机 (state\_machine)

按顺序经历多个**阶段**，每阶段都要等条件为真才能进入下一阶段。适合实现复杂的**多阶段流程控制**。

**核心概念：**

- **状态列表（states）**：用 `→` 连接的各阶段**名称标签**（纯文本，不是节点名也不是变量名），仅用来标记当前处于第几个阶段
- **cond端口**：所有阶段共用同一个条件——每阶段都检查这个条件是否为真
- **失败回退（fail\_state）**：条件为假时跳回到哪个阶段重新开始

**画布连接方式：**

```
[条件检测] ──result(bool)──→ [state_machine].cond(data_bool)
                                    │
                               done(全部完成)──→ [loop_while] 循环回来
```

**参数详解：**

| 参数       | 说明                         | 示例                    |
| -------- | -------------------------- | --------------------- |
| 状态列表     | 各阶段的名称标签，用→连接              | `待机→攻击→冷却→待机` (4阶段循环) |
| 失败回退     | 条件失败时回退到的阶段名（必须与状态列表中名称匹配） | `待机` (任何阶段失败都回到待机)    |
| 轮询间隔(ms) | 每次检测条件之间的等待时间，默认100ms      | `200` = 降低CPU占用但响应变慢  |

**执行过程示例（状态列表: 待机→攻击→冷却→待机）：**

```
【阶段0: 待机】 检测 cond → false? → 回退到"待机"(保持)
                         → true?  → 进入阶段1 ✓
【阶段1: 攻击】 检测 cond → false? → 回退到"待机"
                         → true?  → 进入阶段2 ✓
【阶段2: 冷却】 检测 cond → true?  → 进入阶段3 ✓
【阶段3: 待机】 检测 cond → true?  → 全部完成 → 输出 done ✅
```

> **典型用途**：
>
> - 游戏战斗自动化：`待机→攻击→冷却→待机` 循环
> - 多步骤登录流程：`登录→选区→进入游戏` 线性流程
> - Boss战阶段管理：`阶段1→阶段2→阶段3→结算`

#### 跳转 (goto)

跳转到画布上的另一个节点。支持在 Fork/Race 分支内正常工作。

#### 调用宏

调用已有的旧格式宏脚本（`.json` 文件）。

| 模式   | 说明             |
| ---- | -------------- |
| 同步调用 | 等宏执行完再继续       |
| 异步调用 | 启动宏后立刻继续，宏在后台跑 |

异步调用有两个输出端口：

- **完成**：宏正常执行完毕
- **中断**：宏被手动停止

### 3.5 并发控制节点

这是 MacroDriver 最强大的功能——**同时做多件事**。

#### 并发执行 (Fork)

同时启动多个分支，各做各的。

```
                    ┌→ [分支1：自动攻击]
[开始] → [Fork] ────┤
                    └→ [分支2：监视血量]
```

Fork 有两个输出端口：

| 端口     | 什么时候执行      | 适用场景      |
| ------ | ----------- | --------- |
| **立即** | 分支启动后立刻执行   | 需要继续做其他事  |
| **完成** | 等所有分支都跑完才执行 | 等所有事做完再继续 |

> **常见疑问**："完成"端口和 Join 节点有什么区别？
>
> - **完成端口**：简单场景用，等所有分支跑完自动汇合，不用额外连线
> - **Join 节点**：复杂场景用，可以跨层级汇合、可以选"任意一个到达就触发"
>
> 两者都保留，按需选择。

#### 汇合 (Join)

等待多个分支到达后继续。

| 参数   | 说明                                                 |
| ---- | -------------------------------------------------- |
| 等待模式 | **全部**：等所有分支到达；**任意**：任意一个到达就触发；**自定义**：指定哪些分支必须到达 |
| 超时   | 最多等多久（毫秒）                                          |
| 取消其他 | 条件满足后是否取消还没到的分支                                    |

> ⚠️ **注意**：Join 节点设计用于"等待一组分支完成"的一次性汇合场景，**不建议在循环内重复使用同一个 Join 节点**。如果需要在循环中等待多分支完成，请将 Join 放在循环外部，或每次循环创建新的流程结构。

#### 竞速 (Race)

多个分支同时跑，**谁先完成谁赢**，其他分支自动取消。

```
                    ┌→ [分支1：检测怪物A出现]
[开始] → [Race] ────┤
                    └→ [分支2：检测怪物B出现]
                    （谁先检测到，就执行谁的应对策略）
```

> **重要**：Race 分支跑到最后自动算赢，不需要额外操作。如果你想提前宣告胜利（不等分支跑完），在分支里放一个"宣告胜出"节点。

#### 宣告胜出 (race\_win)

放在 Race 分支里，不等分支跑完就宣告胜利。在节点面板中以高亮颜色显示。

> **提示**：race\_win 不是必须的。分支自然结束也会自动胜出。只有当你需要"提前抢占"时才用它。

#### 停止分支 / 暂停分支 / 恢复分支

控制其他分支的状态。

***

### 3.6 变量类节点（青色）

变量就像一个"储物箱"，你可以把数字、文字存进去，后面再取出来用。

#### 设置变量

| 参数  | 说明                     |
| --- | ---------------------- |
| 变量名 | 给储物箱起个名字               |
| 值   | 存什么进去（支持 `${其他变量}` 引用） |
| 类型  | 字符串 / 数字 / 布尔          |

也支持批量设置多个变量。

#### 变量运算

对数字做加减乘除等运算。

#### 变量比较

比较两个值的大小。

> **提示**：比较时会自动判断类型——先尝试当数字比，比不了就当文字比。比如 `"10" > "2"` 会按数字比较（结果为真），`"hello" > "world"` 会按文字比较。这样你不需要手动转换类型。

#### 字符串处理

拼接、截取、替换、分割文字。

#### 类型转换

在数字和文字之间转换。

***

### 3.7 工具类节点（黄色）

#### 坐标书签

给一个坐标起个名字，以后用 `@书签名.x` 和 `@书签名.y` 来引用。

> **重要**：书签的坐标是**实时解析**的。如果你用的是窗口坐标模式，每次引用书签时都会重新查询窗口位置。这意味着你把窗口拖到别的地方，书签坐标会自动跟着变。

#### 日志输出

在控制台输出一段文字，方便调试。

***

### 3.8 预设节点（粉色）

预设节点是常用组合的快捷方式：

| 节点   | 等于                 |
| ---- | ------------------ |
| 预设点击 | 坐标解析 + 鼠标移动 + 鼠标点击 |
| 找图点击 | 截图 + 图片匹配 + 鼠标点击   |
| 读取文字 | 截图 + OCR + 存入变量    |

## 四、常见使用模式

### 4.1 游戏自动打怪


## 五、常见疑问解答 (FAQ)

### Q1：为什么我的自动化跑到结束节点后，其他分支也停了？

**这是设计如此。** 结束节点是"全局停止"——任何一个分支到达结束节点，整个自动化全部终止。如果你只想结束当前分支，不要放结束节点，让分支自然跑完就行。

### Q2：Fork 的"完成"端口和 Join 节点有什么区别？该用哪个？

- **简单场景用"完成"端口**：等所有分支跑完自动汇合，不需要额外连线
- **复杂场景用 Join 节点**：需要跨层级汇合、或者只需要等"任意一个"分支到达时

### Q3：Race 分支跑完了，会自动赢吗？

**会。** 分支自然执行完毕就自动算胜出，不需要放 race\_win 节点。race\_win 只在你想"提前宣告"（不等分支跑完就抢占胜利）时才需要。

### Q4：我在分支里用了 goto，为什么没跳转？

这是已知 bug，goto 在并发分支内可能不生效。建议在主流程中使用 goto。此问题待修复。

### Q5：变量是每个分支独立的吗？

**不是。** 所有变量是全局共享的——任何分支都能读写任何变量。你需要自己管理变量名，避免多个分支同时修改同一个变量导致混乱。

### Q6：书签坐标会跟着窗口移动吗？

**会。** 如果你用的是窗口坐标或相对坐标模式，每次引用书签时都会重新查询窗口位置。你把窗口拖到别的地方，书签坐标自动跟随。

### Q7：OCR 检测好慢，怎么办？

OCR 本身就需要时间（50\~200ms）。建议：

1. 开启**缓存策略**——画面没变化就跳过识别
2. 缩小检测区域——只截取需要识别的部分
3. 增大检测间隔——不需要每帧都识别

### Q8：监视器的"自动停止"关了之后，它是怎么工作的？

关闭自动停止后，监视器触发 → 执行 trigger 端口后面的节点 → 等那个节点执行完 → 继续监视。每次只等一个下游节点。

### Q9：怎么搜索节点最快？

在左侧搜索框直接输入拼音！比如：

- 输入 `bingfa` → 找到"并发执行"
- 输入 `dianji` → 找到"鼠标点击"、"预设点击"、"找图点击"
- 输入 `if` → 找到"条件判断"

也支持中文和英文搜索。

### Q10：调用宏时，同步和异步有什么区别？

| <br /> | 同步调用    | 异步调用                      |
| ------ | ------- | ------------------------- |
| 行为     | 等宏跑完再继续 | 启动宏后立刻继续                  |
| 适用     | 需要等宏结果  | 后台执行，不阻塞                  |
| 输出端口   | 只有 next | 有 completed 和 interrupted |

### Q11：为什么我调用一个很短的宏，感觉有些设置没生效？

当宏只有 1\~2 步时，系统会走"快速通道"直接执行，跳过一些旧引擎的特性（如随机延迟、延迟补偿等）。这是有意的优化——简单动作不需要这些开销。

### Q12：变量比较时，"10"和"2"比较，结果是"10大于2"吗？

**是的。** 比较时会自动尝试转成数字——`"10"` 和 `"2"` 会按数字比较，10 > 2 为真。如果转数字失败（比如 `"hello"` 和 `"world"`），才会按文字比较。这样你不需要手动转换类型。

### Q13：条件判断节点没连数据线会怎样？

会使用"默认结果"参数（默认走 false 分支）。这不是 bug——简单场景下你不需要连数据线，直接在参数里设好走哪条分支就行。

### Q14：Join 超时了会怎样？

超时后仍然走 done 端口继续执行，不管到了几个分支。不会区分"全部到达"和"超时"。

### Q15：多个监视器同时跑会冲突吗？

不会。每个监视器有独立的轮询线程，互不影响。但注意它们共享截图资源——如果都开启了 DXGI 截图源，会共用同一个截图流。

## 六、小技巧

1. **善用书签**：把常用的坐标存为书签，以后改坐标只需要改书签，不用逐个节点改
2. **先测试再组合**：每个检测节点单独测试通过后，再组合成复杂流程
3. **用日志调试**：在关键位置放日志输出节点，运行后看控制台确认流程走到了哪里
4. **缩小检测区域**：OCR 和图片匹配时，尽量缩小搜索区域，速度会快很多
5. **合理使用缓存**：画面不常变化的场景，开启帧差缓存能大幅提升性能
6. **注意变量命名**：变量全局共享，起名时加上前缀避免冲突（如 `farm_x`、`battle_hp`）
