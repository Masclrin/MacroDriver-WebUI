# 后续高难项说明（T3-2 / T3-4 / T3-5 / T3-6）

> 面向非专业读者：每一项都按「**是什么 → 怎么实现 → 有什么用 → 有什么影响/风险**」写清楚。
> 原则：**任何"提精度"的改动都要说明 CPU 代价**；任何"改执行内核"的改动都必须先有回归测试。

---

## 先说结论：建议顺序

| 顺序 | 项 | 风险 | 收益 | 建议 |
|---|---|---|---|---|
| ① | **T3-5 性能收尾** | 中（核心路径，但有测试可依） | **最高**：直接降占用、降卡帧 | 优先做，分三小步独立提交 |
| ② | **T3-6 递归改迭代** | 中高（调度循环重写） | 中：消除大流程崩溃 | ② 做，先补大流程回归 |
| ③ | **T3-4 状态机逐阶段条件** | 低（格式迁移，不碰执行精度） | 中：流程表达力 | ③ 做，需带旧格式迁移 |
| ④ | **T3-2 网络状态整形** | 高（要装驱动、属外部工具） | 场景专用 | 等专用软件，本工程只留接口 |

> 之所以把"最难的"排后面：①③ 不会改变宏的时序精度，②④ 会碰到执行内核或系统层，
> 需要更多验证成本。

## T3-5 性能收尾（**最值得先做**）

它其实是**三件独立的小事**，合起来解决你提过的"自动化流程占用高、不符合高帧率场景"。

### 5-a Fork / Join / Race 从"轮询"改成"事件通知"
- **现状**：并发分支（Fork 分叉、Join 汇合、Race 竞速）判断"某个分支跑完了没"，
  用的是**每隔 50~100ms 去看一眼**（轮询）。
  → 后果：一次并发闭环至少多等 ~100ms；这 100ms 里线程还在醒着看，**既拖时序又占 CPU**。
- **怎么实现**：分支结束时**主动通知**（`threading.Event` / `Condition`），等待方立刻醒来。
  类比：从"每 5 分钟去门口看快递到没到"改成"快递到了按门铃"。
- **有什么用**：并发闭环延迟从 **≥100ms 降到 <1ms**；轮询线程不再空转 → **直接省 CPU**。
- **影响/风险**：
  - 改的是**并发同步机制**，属于核心执行路径 → 必须补回归（现有
    `automation/tests/test_engine_realtime.py` 可扩展）。
  - 正确性风险点：分支被取消 / 异常退出时也要 `set()` 事件，否则会**死等**。
    （现有代码里"分支被取消后状态被覆写成 completed"就是同类历史 bug，要一起防。）
  - 对宏时序精度**无负面影响**（只减少等待）。

### 5-b 单次点击的"按下-抬起固定 10ms"改为可配置
- **现状**：`engine.py` 里一次点击固定按下 10ms 再抬起，双击 40ms，**不能关**。
- **怎么实现**：暴露成参数（默认 1ms，或由动作节点单独指定）。
- **有什么用**：减少"每次点击都白等 10ms"的累计延迟。
- **影响/风险**：极小。个别老游戏/驱动对**过短的按下时间**可能识别不到点击
  （表现：偶尔没点中）→ 所以保留可配置，并**默认不要极端到 0ms**。

### 5-c 节点失败重试默认 3 次 × 500ms → 默认 0 次
- **现状**：节点出错默认重试 3 次、每次等 500ms，而且**会重放非幂等动作**（比如重复按键）。
- **怎么实现**：默认改成 0 次重试（要重试的流程由用户显式开启）。
- **有什么用**：消掉"静默卡 1.5 秒 + 重复输入"这两个最烦人的副作用。
- **影响/风险**：原本依赖"重试兜底"的流程，偶发失败后**不再自动恢复** →
  行为会变（更快失败，更快暴露问题）。这是**行为变更**，需要在使用说明里写明。

## T3-6 递归派发改迭代（消除"大流程崩溃"）

- **现状**：执行流程图靠 Python **递归**推进（节点调用子流程、子流程再调用节点）。
  递归层数 = 节点数 → 约 **340 个节点的线性链就会栈溢出**（RecursionError，表现为"莫名报错/中断"）。
- **怎么实现**：把递归换成**显式栈 + 循环**（自己维护一个"待执行节点"列表）；
  已有的 `goto` 跳转 trampoline 保留。
  类比：从"函数一层层套娃"改成"用一张待办清单逐个划掉"。
- **有什么用**：支持几百~几千节点的复杂流程，不再中途崩。
- **影响/风险**：
  - 改的是**引擎调度主循环**，功能应当**完全等价**，但任何等价性 bug 都很难查 →
    必须先有**大流程端到端回归**（构造 1000 节点链 + 嵌套循环 + goto，跑通并断言步数）。
  - 对精度/占用**无直接影响**（只是把调用栈换成堆上的列表，内存占用反而更可控）。

## T3-4 状态机"逐阶段独立条件"

- **现状**：状态机有"阶段列表"（如 `待机 → 攻击 → 冷却`），但**所有阶段共用同一个判定条件**。
- **怎么实现**：把存储格式从**字符串** `"A→B→C"` 改成**结构化数组**：

  ```json
  [ {"name":"待机","cond_ref":"节点3.result","timeout_ms":0,"fail_state":""},
    {"name":"攻击","cond_ref":"节点5.result","timeout_ms":800,"fail_state":"待机"} ]
  ```

  并写**旧格式迁移**：读到 `"A→B→C"` 自动转成数组（`cond_ref` 沿用原来的共用条件）→ **旧脚本照常能跑**。
- **有什么用**：每个阶段可以用**不同的判定条件**、**独立超时**、**独立失败回退**，
  更贴近"待机看 A、攻击看 B、冷却看 C"的真实战斗循环。
- **影响/风险**：
  - 属于**破坏性变更（存储格式）**，但有迁移就是兼容的；单元测试要覆盖"旧格式读入 → 新格式保存 → 再读回"。
  - **不影响精度与 CPU 占用**（只是控制流表达力）→ 是四项里**风险最低**的一个。

## T3-2 网络状态整形（正常 / 断网 / 弱网 / 强网）

- **现状**：只有接口位置（`["ext","net.set","weak"]` 的**描述符**已在系统里注册），**没有实现**。
- **怎么实现**：Windows 下需要**内核级网络过滤**（WinDivert / WFP 调用）或进程级限速器，
  由**专用软件/插件**完成；本工程只负责把指令交给它（`register_ext_handler`）。
- **有什么用**：复现断线重连、弱网抖动、卡顿；也可反向"强网"降低丢包和延迟波动。
- **影响/风险（较高，所以要等专用软件）**：
  - 需要**装驱动/管理员权限**；网络类驱动容易被**反作弊**视为异常 → 只在非竞技/测试场景用。
  - 断网状态下会**真的掉线**，可能触发游戏的惩罚机制。
  - 本工程不改内核 → 项目本身不会被它拖累，风险都封在插件里。

## 一句话总览

| 项 | 会不会劣化现有项目 |
|---|---|
| T3-5-a 事件化 | 只会**变好**（省 CPU、降延迟）；风险是"漏通知导致死等"，用测试挡住 |
| T3-5-b 点击间隔可配 | 只会变好；默认值不要取极端 |
| T3-5-c 重试默认 0 | 行为变更（失败更快暴露），不是性能劣化 |
| T3-6 递归改迭代 | 功能等价；风险在"等价性 bug"，靠大流程回归兜 |
| T3-4 状态机格式 | 兼容迁移后无劣化风险 |
| T3-2 网络整形 | 风险在外部驱动，与项目本体隔离 |
