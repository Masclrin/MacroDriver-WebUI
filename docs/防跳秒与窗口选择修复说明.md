# 防跳秒插件与窗口选择修复说明

> 对应反馈：
> 1. 检查插件「防跳秒」亮屏(白屏)检测超时，是否有再次点击快捷键恢复帧率；
> 2. 含「窗口句柄变量名」的「选择窗口」按钮在 WebUI 聚焦时提示「未找到可见窗口」；
> 3. 检查 DXGI 等截图源问题；
> 4. 外置脚本 `防跳秒精简版.py` 可识别任意全屏独占/窗口化程序，而插件「常见不触发」。

---

## 一、结论速览

| 反馈 | 结论 | 处理 |
|------|------|------|
| ① 亮屏超时是否补发恢复键 | **原本已有**（`0772736` 加入），但"截图通道失效"时会白等到超时 | 保留 + 强化：截图不可用立即按超时处理并恢复；所有退出路径统一补发 |
| ② 选择窗口提示「未找到可见窗口」 | 后端枚举本身正常（实测 17~18 个窗口，耗时 <1ms），失败面在调用链的异常/序列化/时序 | 后端加固 + 前端自动重试 + 手动填写兜底 |
| ③ DXGI 截图源 | **真 Desktop Duplication 在本机不可用**，一直静默退化为"全屏 BitBlt"；且回退模式下仍按 60fps 跑，占满 CPU | 取帧缺陷修复 + 回退模式限速 + 明确的降级提示 |
| ④ 插件常见不触发 | **根因：坐标退化**（hwnd 失效 / 窗口最小化 → 区域变成零面积） | 退化检测 + 自动回退（屏幕绝对坐标 / 绝对像素） |

## 二、④ 插件「常见不触发」——根因与修复（最关键）

### 根因（已复现）

插件默认 `mode=relative`（窗口内比例坐标）。`engine/coordinate.py:resolve_region` 在
下列场景会算出**零面积区域**：

| 场景 | `GetClientRect` / `ClientToScreen` 结果 | 换算后区域 |
|------|------------------------------------------|-----------|
| `hwnd` 失效（游戏重启后变量里残留旧句柄） | `(0, 0, 0, 0)` | `(0, 0, 0, 0)` |
| 窗口已最小化 | `(-32000, -32000, 0, 0)` | `(-32000, -32000, 0, 0)` |

实测（`1932x1080`）：

```
relative + 失效 hwnd:
   黑屏 (0, 0, 0, 0)     ← is_black 恒为 False
   亮屏 (0, 0, 0, 0)     ← is_bright 恒为 False
   点击 (0, 0, 0, 0)     ← rx<=mx<=rx+rw 恒不成立 → 组合永不匹配
```

零面积区域下：

* `DXGICapture.get_region_frame` 命中 `x2 <= x1` → 返回 `None` → 检测函数返回 `False`；
* `ComboWatcher` 的点击判定 `0 <= mx <= 0` 恒不成立。

结果就是**插件完全不触发，而且没有任何日志**。外置脚本 `防跳秒精简版.py` 用的是屏幕
绝对坐标，完全不依赖窗口句柄，所以它对任意全屏独占/窗口化程序都能工作 —— 这正好解释了
"外置脚本能用、插件不触发"。**已排除截图位置不准、以及"全屏截图 vs 区域截图"的差异**：
实测同一区域下"区域截图"与"全屏截图+本地切片"内容一致（差异仅来自两次截图之间的画面变化）。

### 修复

`plugins/anti_jump/backend.py`：

1. `_is_valid_hwnd()`：`IsWindow` + `IsIconic` 校验句柄，失效/最小化时打印警告并放弃该句柄。
2. `_is_usable_region()`：区域必须非零面积、坐标不在屏幕外(`-16000`)、边长合理。
3. `_resolve_region()` 三级兜底：
   * 正常解析 → `resolved`
   * 退化为零面积 → `fallback-screen`（按屏幕尺寸换算，**等价外置脚本的绝对方案**）
   * 仍不可用 → `fallback-absolute`（把框选值当屏幕绝对像素，兼容"切换模式后未重新框选"）
   * 全部失败 → `invalid`：**立即报错返回**，不再静默空转
4. 组合点击区域同样走三级兜底；完全无效时降级为"仅按键触发"并告警。
5. 启动时把解析结果与状态写入日志，方便定位。

## 三、① 亮屏检测超时是否补发恢复键

原实现（`backend.py` 亮屏超时分支）**已经**会补发一次 RTSS 恢复键，并在 `finally` 中对
"异常/停止退出时仍处于锁帧状态"补发。本次在此基础上强化：

* 新增 `CaptureChannel.capture_broken()`：截图通道连续失败（默认 25 次 ≈ 0.5s）即判定不可用。
* 亮屏等待期间若截图失效 → **不再白等满 `bright_timeout`**，立即按超时处理并恢复帧率。
  （原先最多会白等 8 秒才恢复，期间游戏一直处于锁帧状态。）
* 统一 `_restore(reason)`：亮屏确认 / 亮屏超时 / 截图失效 / 停止 / 异常 全部走同一恢复路径。

**不变量：每一次锁帧都必须有一次对应的恢复。** 已由回归测试逐条锁定：

```
A 正常周期            → 锁帧 + 恢复
B 亮屏检测超时        → 锁帧 + 恢复（反馈第①条）
C 黑屏检测超时        → 不锁帧
D 执行前已停止        → 不锁帧
E 等待亮屏时被停止    → 锁帧 + 恢复
F 收到停止信号        → 不锁帧
```

## 四、③ DXGI / 截图源

### 发现

1. **真 Desktop Duplication 在本机不可用。**
   `comtypes.gen` 中没有 `DXGI` / `D3D11` 模块（二者不属于标准 Windows 组件），
   且 `comtypes.client.GetModule("dxgi.dll")` 报 `TYPE_E_CANTLOADLIBRARY`
   （`dxgi.dll`/`d3d11.dll` 本身不含 type library）。
   于是 `_initialize_ctypes()` 生效 → **所谓"DXGI 截图源"其实是每帧一次全屏 BitBlt**。
   其后果：窗口化/无边框程序正常；**独占全屏(D3D)程序通常只能取到黑屏**。
   原提示过于含糊，现改为明确说明降级原因与影响。

2. **取帧缺陷（本次修复）。** `automation/detection/dxgi_capture.py` 原先：
   * 用 `D3D11_MAP_FLAG_DO_NOT_WAIT` 映射**上一帧**的暂存纹理，且**不检查 `Map` 的 HRESULT**：
     GPU 未完成 `CopyResource` 时 `Map` 返回 `DXGI_ERROR_WAS_STILL_DRAWING`，`pData` 为 NULL，
     读取失败被 `except` 静默吞掉 → 该帧为 `None`；
   * 失败分支**不执行 `Unmap`**，纹理状态残留，可能持续取不到帧。
   * 现象：后台"有 DXGI 却经常拿不到新帧 / 只能拿到陈旧帧"，检测漏判。

   改为：映射刚 `CopyResource` 进去的那张暂存纹理，使用**阻塞式 `Map`(flags=0)**，
   校验 HRESULT，并在 `finally` 中确保 `Unmap` —— 与外置脚本一致的取帧方式，
   **每帧都新鲜且有效**。连续 Map 失败则请求重建采集资源。

3. **回退模式限速。** 实测全屏 BitBlt ≈ **19ms/帧**（区域 BitBlt ≈ 6.4ms，MSS ≈ 12.2ms）。
   回退模式下若仍按「截图源」默认 60fps 跑，将占用 **>100% 单核**。现于
   `CaptureManager.start_dxgi()` 中把回退模式的运行帧率上限压到 **20fps**；
   记录到 `_dxgi_fps` 的仍是用户请求值，保证不会被判定为"配置已变"而反复重启。

4. **插件自带采集（新增参数 `自带DXGI采集`，默认开）。**
   流程图里没有启用「截图源」节点时，插件会自建全屏后台采集并按绝对坐标切片
   （与外置脚本一致），使插件不再依赖"截图源"是否启用。
   本机实测 BitBlt 成本较高，帧率取 **15fps**（≈29% 单核，66ms 检测延迟对 0.5s 以上的
   黑屏过场足够）。若流程图已有 DXGI，则不会重复创建；若运行中"截图源"启动，插件自动让路。

### 建议（未改动，需要时再做）

若确实需要真 Desktop Duplication（独占全屏），需在 `comtypes.gen` 中提供由
Windows SDK 的 `dxgi.tlb` / `d3d11.tlb` 生成的 `DXGI.py` / `D3D11.py` 模块；
否则全项目所有截图路径都是 BitBlt/MSS，独占全屏一律只能拿黑屏。

## 五、② 「选择窗口」提示「未找到可见窗口」

### 诊断

* 后端枚举本身**正常**：独立调用 `get_window_list()` 返回 17~18 个窗口，耗时 **<1ms**，
  含 `原神`、`ky3 Launcher` 等；也不会因回调未 `return True` 而提前终止
  （Python 3.12/3.13 实测返回 `None` 不会中断 `EnumWindows`，但该写法仍是错的）。
* 因此失败面前移到**调用链**：异常吞掉 → 返回 `{ok:false}`；或结果无法被 pywebview
  序列化；或一次性时序问题（用户"点一下别的窗口再回来点按钮"就能成功，正是"重试一次"）。

### 修复

后端 `bridge/automation_api.py::get_window_list`：

1. 枚举回调**所有分支都 `return True`**（正确的 `WNDENUMPROC` 契约，避免版本/实现差异下提前结束）。
2. 句柄用 `c_void_p` 传递（不再用 `c_ulong`，避免 32 位截断）。
3. `_clean_window_text()` 清洗标题/类名：剔除孤立代理字符与控制字符，
   **避免单个异常窗口标题让 `json.dumps` 抛错进而整个接口失败**。
4. 结果为空时**放宽条件重试一次**（允许无标题但可见的顶层窗口）。
5. 打印 `[窗口枚举] 共发现 N 个可选窗口`，便于区分"后端没给数据"还是"前端没拿到"。

前端 `webui/modules/auto/pickers/file-pickers.js`：

6. `_fetchWindowList(retries, cb)`：失败或为空时**自动重试 2 次（间隔 150ms）**，
   把用户手动"点开再点回来"的绕行办法自动化。
7. 仍失败时**不再只弹一个死提示**，而是弹出「手动填写窗口句柄 / 窗口标题」输入框兜底。
