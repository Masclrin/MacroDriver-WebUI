## 一、这是什么项目

Windows 本地**高精度宏驱动控制台**（Python + pywebview，无前端框架）。

两大能力：
1. **宏录制/编辑/精确执行** —— 微秒级键鼠回放（`kd/ku/md/mu/view/move_to/scroll/wait/loop/import/ext/custom/note`）
2. **自动化流程可视化编辑** —— 拖拽节点图，Fork/Join/Race 并发、图像/颜色/OCR 检测

关键差异化：双输入驱动（SendInput + Interception 内核注入）+ native **standby** 引擎（C 扩展，
绕过 Python/GIL 直接消费预编译 QPC 时间线）+ PI/前馈延时补偿。

核心约束（改代码前务必读）：**延迟与 CPU 占用是矛盾**。
"提精度"优先用**核隔离/减少重复工作**，而不是提高优先级。详见
`docs/项目需求与持续开发目标.md` 第六节。

## 三、必须知道的约定与坑（省你几小时）

### 3.1 前后端返回值有**两套**约定（最容易踩）
- **扁平**：`bridge/base.py::_ok(**kwargs)` → `{"ok":True, ...字段}`。
  宏文件相关（`read_macro` / `save_macro` / `run_macro_slice`）都是这种。
- **包装**：`bridge/plugin_api.py` 与 `bridge/automation_api.py` 的模块级 `_ok(data)`
  → `{"ok":True, "data":{...}, "error":None}`。

> 历史 bug：「调用宏」节点动作编辑器"能存不能读"，就是因为把扁平返回值当成 `res.data.rows` 读。
> **新写前端代码时先确认目标 API 属于哪一套**；不确定就两种都兼容。

### 3.2 前端"点击后整表重建"会打断双击
编辑器动作列表/标签栏如果**每次点击都重建 DOM**，双击的第二次点击会落在新节点上，
`dblclick` **永远不会触发**（表现为"双击编辑失效""双击重命名失效"）。
现在点击只做**就地高亮**（`updateSelectionHighlight` / `syncTabBarActive`），
只有在需要增删行时才 `renderViewList()`。**改这里务必保持这个原则。**

### 3.3 拖拽事件的 `e.target` 可能是**文本节点**
Chrome 会把拖拽起点报成文字节点，`e.target.closest(...)` 会抛
`closest is not a function`。统一用 `action-list-render.js` 里的 `elFrom(target)`。

### 3.4 选中高亮依赖 `.list` 类
高亮规则是 `.list li.active`。小窗里的 `<ul>` 必须写成 `class="list action-list"`，
少了 `list` 就没有高亮与 hover。

### 3.5 ext 指令**不参与时间线**
`compile_macro` 里 ext 的延时恒为 `0.0`，且 PI/前馈补偿对 `ext` 直接返回 0
→ **插入任意条 ext 都不会位移核心动作的时间线**。改 `compile_macro` 时不要破坏这一点。

### 3.6 未识别行会被**保留为 `{__raw: "原文"}`**
`macro_io/parser.py` 对解析失败/顶层非数组的行不再丢弃，保存时原样写回。
`_list_macro_files` 会跳过 `.`/`__` 开头的文件（测试点运行产生的临时宏）。

### 3.7 Chrome 会缓存 ES 模块 → 截图会截到旧代码
`tools/shot.sh` **每次用全新 profile** 就是为了绕开这个。如果你自己写截图命令，
一定要换 `--user-data-dir`，否则会误判"改动没生效"。

## 四、怎么自检（不用人工核对）

### 4.1 前端截图（无头 Chrome）
```bash
# 1) 起静态服务（无后端，纯 UI；端口随意）
python -m http.server 8793 --directory webui

# 2) 截图（out 用 Windows 风格路径）
bash tools/shot.sh "http://127.0.0.1:8793/index.html?p_tab=editor&p_panes=3" "E:/.../artifacts/preview/x.png"
```
**静态预览 URL 参数**（无后端时生效）：

| 参数 | 作用 |
|---|---|
| `p_tab=editor\|macro\|...` | 预设打开哪个页 |
| `p_panes=1..3` | 预设展开几个编辑小窗 |
| `p_sidebar=collapsed` | 预设侧栏折叠 |
| `p_topbar=collapsed` | 预设顶栏折叠 |
| `p_op=reorder-last-first` | 自检：把最后一个小窗移到最前 |
| `p_op=insert-front\|insert-mid` | 自检：新窗按落点插入 |
| `p_op=bp` | 自检：给示例宏打两个测试点 |
| `p_op=ext` | 自检：灌入示例 ext 描述符并切到 ext 表单 |
| `p_diag=1` | 诊断：把未捕获错误写进 `<title>`，用 `--dump-dom` 读 |

排错示例：
```bash
chrome --headless=new --dump-dom "…/index.html?p_diag=1" | grep -o "<title>[^<]*</title>"
```

### 4.2 后端回归

python -m automation.tests.test_engine_realtime

## 七、给下一个会话的三条提醒

1. **改动前先读** `docs/项目需求与持续开发目标.md` 第六节「开发约束」——尤其"禁止新增 `except: pass`"。
2. **前端改动后跑一次截图自检**（`tools/shot.sh` + 对应 `p_op`），比人工点快得多；
   注意每次都会开新 profile，天然避开缓存。
3. **执行内核的任何改动**（`compile_macro` / `execute_macro_once` / 递归派发 / 并发同步）
   必须先补或扩展回归测试，再改代码——这是本项目最容易"静默劣化"的地方。
