# 自动化引擎 Bug 汇报（含开始/结束节点影响分析）

## 〇、开始/结束节点设计概要

为消除入口选择的歧义、明确执行流的终止，计划增加两个特殊节点：

- **开始节点**（如 `flow/start`）：每个图的唯一执行入口，不接收任何 flow 数据输入，只有一个 flow 输出端口。编译时检测：图中必须且只能有一个开始节点。
- **结束节点**（如 `flow/end`）：显式终止执行，可有一个或多个 flow 输入，无 flow 输出端口。执行到该节点时立即终止整个图（包括所有监视器），与 `stop_event` 等效。

这两个节点将影响编译器入口逻辑、控制流终止语义以及部分现有节点的行为。下文中，凡受该修改影响的 Bug，均会明确指出。

***

## 一、编译器（compiler.py）

### Bug 1.1 \~ 1.4 → **通过开始节点彻底解决**

**原 Bug 汇总：**

- 1.1：纯数据节点可被误选为主入口
- 1.2：有 flow 输入端口的未连接节点被当作入口
- 1.3：`monitor_entry_ids` 收集不完全
- 1.4：入口选择优先级误导

**影响分析：**\
引入开始/结束节点后，编译器不再需要从所有节点中"猜测"入口。规则简化为：

1. 所有执行都从唯一的"开始"节点出发。
2. 监视器仍可作为常驻后台线程，由开始时一并启动，其收集方式改为：遍历所有 `monitor/*` 类型节点，无论是否有连接，均作为监视器线程启动（因为监视器不应依赖 flow 输入连接）。
3. 入口优先级问题彻底消失。

**修复建议：**

- 编译期强制要求图中存在且仅存在一个 "flow/start" 节点，否则编译失败。
- 废弃原有 `entry_node_id` 启发式逻辑，直接使用开始节点。
- 监视器入口直接按类型前缀 `monitor/` 收集，无需再依赖 `has_flow_input` 判断。

**结论：** 以上四个 Bug 可关闭，修改为"通过显式开始节点解决"。

***

### Bug 1.5（新增）：开始/结束节点的连接规则缺乏校验

**优先级：高**

**现象：**\
如果允许用户随意连接，可能出现：开始节点被连接了 flow 输入、结束节点被连了 flow 输出、图中无开始节点或有多个开始节点等，导致运行时行为混乱或异常。

**根因：**\
节点注册系统本身不限制端口连接规则，需编译期补充。

**修复建议：**

- `parse_graph` 阶段强制校验：
  - "开始"节点只能有 1 个 flow 输出，且不能有任何 flow 输入或 data 输入。
  - "结束"节点只能有至少 1 个 flow 输入，不能有 flow 输出或 data 输出。
  - 检测唯一开始节点存在性，否则报错。
- 前端也可配合隐藏非法端口。

### Bug 3.2（新增）：开始/结束节点与其他控制流节点的交互需明确

**优先级：中**

**现象：**

- 如果主图因 `goto` 跳转到某节点，跳过了"结束"节点，执行流可能永不终止。
- 异步任务（`call_script_async`）中调用的宏内部是否应该能看见主图的"结束"信号？当前开始/结束节点仅作用于本图，对异步任务无约束，可能导致不一致。

**修复建议：**

- 编译器强制所有可达路径最终都汇聚到"结束"节点（或有 `stop_event` 触发），若存在不可达或无限循环，应发出警告。
- 异步任务应在主图结束时被强制停止，可通过 `stop_event` 传播实现，设计文档需明确。

## 四、并发与线程安全（monitor / TaskPool）

### Bug 4.1：监视器与主流程共享 `ExecContext` 无同步

**优先级：高（不变）**

开始/结束节点的引入要求"结束"节点能干净地中止所有监视器线程。若变量区域无锁，`stop_event` 设置后仍有低概率写入脏数据。必须在结束逻辑执行前保证线程安全。

***

### Bug 4.2：TaskPool 存在 check-then-act 竞态

**优先级：中（不变）**

同上。

***

### Bug 4.3：监视器内 OCR 引擎重复创建

**优先级：高（不变）**

开始节点触发监视器启动时，应确保共享 OCR Engine 的初始化时机正确，避免监视器各自创建，原修复建议仍有效。

## 五、控制流（goto）

### Bug 5.1：goto 在监视器线程中行为未定义

**优先级：中**

**影响变更：**\
开始/结束节点引入后，主图的执行流必须从开始出发，到结束终止。监视器分支中若存在 `goto`，将破坏该线性模型。**建议在编译期直接禁止监视器节点的触发分支中出现** **`goto`** **节点**，否则编译失败。这将使该 Bug 由"未定义行为"升级为"编译期拦截"。

***

### Bug 5.2：goto 缺乏编译期校验

**优先级：中**

开始/结束节点的引入使得静态分析成为可能。可一并实施：校验所有 `goto` 目标节点存在，且不允许跳转到"开始"节点。修复后此 Bug 可关闭。

## 七、开始/结束节点带来的其他考虑

### 7.1 监视器生命周期管理

- 开始节点执行时，应自动启动所有监视器节点（按类型 `monitor/*` 收集）。
- 主执行流到达"结束"节点或手动停止时，必须通知所有监视器线程退出（通过 `stop_event`），否则程序无法干净结束。
- **潜在问题：** 若某监视器处于长时间 `sleep` 或阻塞等待，退出信号可能延迟（目前 `trigger_event` 已支持超时唤醒，影响可控）。

### 7.2 前端兼容性

- 开始/结束节点需作为内置节点注册，但无需 handler（引擎层特殊处理）。
- 前端需适配：禁止删除唯一开始节点，允许从开始拖出唯一连线，结束节点只能作为终点。
