# 数字匹配节点与动作控制 - 全栈设计计划

## 一、概述

本次需求包含四大模块：

1. **"数字匹配"检测节点** — 基于模板匹配的高速数字识别
2. **"动作控制"节点** — 触发后可控制脚本执行流（停止/暂停/恢复）
3. **移动"执行子脚本"** — 从预设块 → 动作块
4. **开发指南文档** — 记录属性面板渲染问题的根因和规范

## 二、节点 1："数字匹配" (detection/check\_digits)

### 2.1 核心设计思路

* 利用项目已有的 `cv2.matchTemplate` + 金字塔加速（复用 `_match_template_pyramid`）

* 不需要 OCR（杜绝 50\~200ms 的 CPU 消耗），模板匹配只需 0.5\~5ms

* 支持多套字体/颜色：用户在 `templates/` 目录下建子文件夹，如 `templates/white_font/`、`templates/yellow_font/`

### 2.2 模板文件夹约定

```
用户选择的模板根目录/
├── white_font/       ← 子文件夹名即字体/颜色方案
│   ├── 0.png         ← 数字 0 模板
│   ├── 1.png
│   ├── ...
│   └── 9.png
├── yellow_font/
│   ├── 0.png
│   ├── ...
│   └── 9.png
└── red_bold/
    ├── 0.png
    ...
```

每个数字模板（0-9.png）从目标截图区域中截取。引擎自动扫描所有子文件夹。

```python
    "hwnd_var":        {"type":"string","default":"","showWhen":"mode=window,mode=relative","varRef":True},

    "wait_timeout_ms": {"type":"number","default":5000,"description":"等待超时(ms), 0=无限等待","showWhen":"wait=true","varRef":True},

```

### 2.5 执行流程（handler）

```
_handle_check_digits(node, ctx):
  1. 解析参数: mode, rect, hwnd, template_folder, threshold,
     digit_width, compare_op, compare_value, wait 等
  2. 从 template_folder 加载所有子文件夹的 0-9.png 模板
     (首次加载后缓存到 ctx 中，key=template_folder 的 hash)
  3. 进入等待循环 (if wait):
     a. 截图数字区域
     b. 预处理: 灰度化 → 二值化(OTSU) → 形态学去噪
     c. 数字切割:
        - 如果 digit_width>0: 等宽切割
        - 否则: 轮廓检测 + 从左到右排序
     d. 对每个切割出的数字块:
        - 对所有字体方案的 0-9 模板逐一 matchTemplate
        - 记录最高置信度的数字
        - 如果最高置信度 < threshold，标记为识别失败
     e. 组合识别结果，例如 "1234"
     f. 数值比较 (if compare_op != "none"):
        - 将识别结果转为数字，与 compare_value 比较
        - 达标 → 走 pass 分支
        - 未达标且 wait=true → 等待 wait_interval_ms 后重试
        - 未达标且 wait=false → 走 fail 分支
     g. 无比较时: 识别成功 → pass, 失败 → fail
  4. 存储结果: ctx.check_results[node_id.digit_value], store_var
```

### 2.6 关键实现细节

**模板加载与缓存:**

```python
# 首次加载后存入 ctx 缓存，避免重复 IO
cache_key = f"digit_templates_{hash(template_folder)}"
templates = ctx._digit_template_cache.get(cache_key)
if not templates:
    templates = _load_digit_templates(template_folder)
    ctx._digit_template_cache[cache_key] = templates
```

**\_load\_digit\_templates 实现:**

```python
def _load_digit_templates(root_folder):
    result = {}  # {"font_name": {0: mat, 1: mat, ..., 9: mat}}
    for font_dir in os.listdir(root_folder):
        font_path = os.path.join(root_folder, font_dir)
        if not os.path.isdir(font_path): continue
        font_templates = {}
        for digit in range(10):
            img_path = os.path.join(font_path, f"{digit}.png")
            if os.path.exists(img_path):
                font_templates[digit] = cv2.imread(img_path, cv2.IMREAD_GRAYSCALE)
        if font_templates:
            result[font_dir] = font_templates
    return result
```

**数字切割:**

```python
# 等宽切割（快）
if digit_width > 0:
```

**匹配:**

```python
best_overall = None, 0.0
for font_name, font_templates in templates.items():
    for digit_val, template in font_templates.items():
        # 跳过比 ROI 大的模板
        if template.shape[0] > roi.shape[0] or template.shape[1] > roi.shape[1]:
            continue
        result = cv2.matchTemplate(roi, template, cv2.TM_CCOEFF_NORMED)
        _, max_val, _, _ = cv2.minMaxLoc(result)
        if max_val > best_overall[1]:
            best_overall = (digit_val, max_val, font_name)
```

### 2.7 分支执行

```python
# 达标 → "pass"
ctx.check_results[f"{node.id}.digit_value"] = int(digit_str) if digit_str else 0
```

## 三、节点 2："动作控制" (action/flow\_control)

### 3.1 设计目标

源自监视器（monitor）的 `on_trigger` / `_apply_on_trigger` 机制，但做成独立节点，可与任何检测节点的分支配合使用。

典型用法：数字匹配的 `pass` 分支 → 动作控制节点 → 停止子脚本/所有任务

### 3.2 节点定义

| 属性            | 值                                 |
| ------------- | --------------------------------- |
| type          | `action/flow_control`             |
| category      | `action`                          |
| display\_name | `动作控制`                            |
| color         | `#22c55e`（同动作节点）                  |
| icon          | `fa-solid fa-sliders`             |
| inputs        | `[{"name":"in","type":"flow"}]`   |
| outputs       | `[{"name":"next","type":"flow"}]` |
| handler       | `_handle_flow_control`            |

### 3.3 参数定义

```python
{
    "action":           {"type":"string","enum":["stop_all","stop_task","pause_task","resume_task","stop_self","nothing"],"default":"stop_all","description":"控制动作","display_names":{"stop_all":"停止所有任务","stop_task":"停止指定任务","pause_task":"暂停指定任务","resume_task":"恢复指定任务","stop_self":"停止自身(当前脚本)","nothing":"无操作(占位)"}},
    "target_task":      {"type":"string","default":"","description":"目标任务ID","showWhen":"action=stop_task,action=pause_task,action=resume_task","nodeRef":"script_block/call_script_async,preset/preset_sub_script","varRef":True},
}
```

### 3.4 执行逻辑

```python
def _handle_flow_control(node, ctx):
    action = node.params.get("action", "stop_all")
    target_task = _resolve_value(node.params.get("target_task", ""), ctx)
    
    if action == "stop_all":
        ctx.stop_event.set()
        ctx.task_pool.stop_all()
    elif action == "stop_self":
        ctx.stop_event.set()
    elif action in ("stop_task", "pause_task", "resume_task"):
        # 复用 monitor 的 _apply_on_trigger 逻辑
        _apply_on_trigger(action.replace("_task", ""), target_task, ctx)
    
    _execute_flow(node.id, "next", ctx)
```

### 3.5 与监视器的区别

| 维度      | 监视器的 on\_trigger | 动作控制节点         |
| ------- | ---------------- | -------------- |
| 触发方式    | 条件检测触发后自动执行      | 作为流程节点，被动被调用   |
| 执行时机    | 异步（监视线程中）        | 同步（主执行流中）      |
| 是否有后续节点 | 无（或自动循环）         | 有 next 端口继续执行流 |

## 五、模块 4：开发指南 - 属性面板渲染问题

### 5.1 问题根因

前端 `nodes.js` 中的 `_registerFallback()` 函数包含了**所有内置节点的硬编码** **`params_schema`**，在某些场景下（后端 API 失败 / 浏览器开发模式）会覆盖后端传来的正确 schema。

### 5.2 规范

**凡是新增或修改后端节点参数，必须同步更新三处：**

| 位置            | 文件                                  | 说明                                                                       |
| ------------- | ----------------------------------- | ------------------------------------------------------------------------ |
| ① 后端节点定义      | `automation/nodes/<category>.py`    | `params_schema`（Python，用 `description`/`enum`）                           |
| ② 前端 fallback | `webui/modules/auto/core/nodes.js`  | `_registerFallback()` 内对应 type 的 `params_schema`（JS，用 `label`/`options`） |
| ③ 后端 handler  | `automation/handlers/<category>.py` | 读取新参数的逻辑                                                                 |

### 5.3 参数格式对照

| Python 后端                         | JS 前端 fallback                 |
| --------------------------------- | ------------------------------ |
| `"type": "boolean"`               | `type: 'bool'`                 |
| `"type": "string", "enum": [...]` | `type: 'enum', options: [...]` |
| `"description": "说明"`             | `label: '说明'`                  |
| `"showWhen": "key=True"`          | `showWhen: 'key=true'`（小写！）    |
| `"display_names": {"a":"A"}`,     | `display_names: {'a':'A'}`     |
| `"default": True`                 | `default: true`                |
| `"default": 0`                    | `default: 0`                   |
| `"varRef": True`                  | `varRef: true`                 |

### 5.4 检查清单

* [ ] 后端 `nodes/<cat>.py` 的 `register()` 中添加了 params\_schema

* [ ] 前端 `nodes.js` 的 `_registerFallback()` 中对应 type 的 params\_schema 已同步

* [ ] 后端 handler 已实现新参数读取逻辑

* [ ] `nodeRef` 引用（如有涉及 type 变更）已全部更新

* [ ] `Grep` 搜索旧 type 名称，确认无遗漏引用
