## 1. 项目现状简述

### 1.1 当前架构

本项目是一个可视化宏/自动化执行引擎，采用节点流图（Node-based Flow Graph）驱动执行。核心模块包括：

- **编译器** (`automation/compiler.py`)：将前端 JSON 流图编译为可执行结构 `ExecGraph`
- **执行引擎** (`automation/engine.py`)：维护 `ExecContext`，驱动节点按流图顺序执行
- **节点注册中心** (`automation/registry.py`)：`PluginRegistry` 统一管理所有节点类型定义
- **检测模块** (`automation/detection/`)：包含颜色、OCR、图像匹配、截图等子模块
- **处理器** (`automation/handlers/`)：每个节点类型对应一个 handler 函数，接收 `ExecNode` 和 `ExecContext`

### 1.2 当前检测模块实现

| 模块   | 文件                      | 功能         | 当前实现                                                       |
| ---- | ----------------------- | ---------- | ---------------------------------------------------------- |
| 截图   | `capture.py`            | 屏幕区域截取     | `mss` 库封装，全屏或区域截取                                          |
| 颜色检测 | `color.py`              | 区域颜色判断     | `np.linalg.norm` 欧氏距离，支持 exact/center/mean/max_diff/change |
| OCR  | `ocr.py`                | 文字识别       | `rapidocr_onnxruntime` 封装，含帧差异/时间间隔缓存                      |
| 图像匹配 | `handlers/detection.py` | 模板匹配       | `cv2.matchTemplate`，每次从硬盘 `cv2.imread` 读取模板                |
| 屏幕状态 | `handlers/detection.py` | 黑屏/亮屏/冻结检测 | 灰度均值比较                                                     |

### 1.3 当前节点定义

**检测节点** (`automation/nodes/detection.py`)：

- `detection/check_color` — 颜色检测
- `detection/check_ocr` — OCR识别
- `detection/check_image` — 图像匹配
- `detection/check_screen` — 屏幕状态

**监视器节点** (`automation/nodes/monitor.py`)：

- `monitor/monitor_color` — 颜色监视（无输入端口，执行图时自动并行启动）
- `monitor/monitor_ocr` — OCR监视
- `monitor/monitor_timer` — 定时器

### 1.4 当前性能瓶颈

1. **截图延迟高**：`mss` 每次截图需 20-50ms，且无法利用局部区域优化
2. **模板重复读取**：`cv2.imread` 每次从硬盘读取，无内存缓存
3. **颜色检测算法未优化**：使用 `np.linalg.norm`（含平方根运算），未利用 OpenCV SIMD 优化
4. **检测节点无等待能力**：只能单次检测，用户需在外部用循环+等待节点实现"轮询直到满足"
5. **无共享帧缓冲**：多个检测节点连续执行时，各自独立截图，重复开销

---

## 2. 优化目标

| 目标       | 指标                              |
| -------- | ------------------------------- |
| 单次局部检测延迟 | 从 ~30-50ms 降至 ~0.5-3ms（使用共享帧缓冲） |
| 截图本身延迟   | 从 ~20-40ms(mss) 降至 ~3-8ms(DXGI) |
| 模板匹配大区域  | 从 ~100-300ms 降至 ~15-40ms（图像金字塔） |
| 模板读取     | 从 ~5-20ms/次 降至 ~0.01ms/次（内存缓存）  |
| 用户开发体验   | 检测节点内置"等待直到满足"能力，无需外部循环         |

## 3. 详细设计方案

### 3.1 新增模块：DXGI 截图引擎 (`automation/detection/dxgi_capture.py`)

#### 3.1.1 设计目标

提供基于 DXGI Desktop Duplication API 的高性能截图能力，支持后台持续采集。

#### 3.1.2 技术方案

- 使用 `ctypes` + `comtypes` 直接调用 Windows DXGI API，不引入额外依赖
- 创建 `D3D11Device` → 获取 `IDXGIOutputDuplication` → 循环 `AcquireNextFrame`
- 帧数据以 BGRA 格式获取，转换为 numpy array 后存入共享缓冲区

#### 3.1.3 类设计

```

DXGICapture (单例模式)
├── __init__()
│   └── 初始化状态：device=None, duplication=None, frame_buffer=None, _lock, _thread, _running
├── initialize(adapter_idx=0, output_idx=0) → bool
│   └── 创建 D3D11 设备，获取指定显示器输出，创建 Duplication
├── acquire_frame(timeout_ms=100) → np.ndarray | None
│   └── 单帧获取：AcquireNextFrame → CopyResource → Map → 转 numpy → ReleaseFrame
├── start_background(fps=60) → bool
│   └── 启动 daemon 线程，循环 acquire_frame 存入 frame_buffer
├── stop_background()
│   └── 设置 _running=False，等待线程结束，释放 duplication
├── get_latest_frame() → np.ndarray | None
│   └── 线程安全地拷贝 frame_buffer
├── get_region_frame(left, top, width, height) → np.ndarray
│   └── 从 frame_buffer 做 numpy slice [top:top+h, left:left+w]
└── is_running() → bool

```

#### 3.1.4 异常处理

- 初始化失败（如不支持 Desktop Duplication、权限不足、远程桌面会话）→ 返回 `False`，上层 fallback 到 BitBlt
- 帧获取超时 → 返回上次缓存帧
- 设备丢失（如显示器切换、分辨率变更）→ 自动尝试重新初始化一次，失败则停止

#### 3.1.5 性能预期

- 后台采集帧率：稳定 60 FPS（受显示器刷新率限制）
- 单帧获取延迟：`AcquireNextFrame` 通常 1-3ms
- 从共享缓冲区 slice 区域：~0.1-0.3ms（纯内存操作）

### 3.2 新增模块：截图管理器 (`automation/detection/capture_manager.py`)

#### 3.2.1 设计目标

统一管理所有截图请求，根据当前状态选择最优截图路径，作为检测模块的唯一截图入口。

#### 3.2.2 类设计

```

CaptureManager (与 ExecContext 绑定，每图执行一个实例)
├── __init__(ctx: ExecContext | None)
│   └── dxgi: DXGICapture | None, _bitblt_fallback_enabled=True
├── start_dxgi(fps=60, region=None) → bool
│   └── 初始化并启动 DXGICapture 后台线程
├── stop_dxgi()
│   └── 停止 DXGICapture
├── capture(region=None, prefer_dxgi=True) → np.ndarray
│   ├── 如果 dxgi 正在运行 → 从 dxgi.get_region_frame() 获取
│   ├── 否则如果 region 较小 (< 500x500) → _capture_bitblt(region)
│   └── 否则 → _capture_mss(region)
└── _capture_bitblt(region) → np.ndarray
    └── Win32 API: GetDC → CreateCompatibleDC → CreateCompatibleBitmap → BitBlt → GetDIBits

```

#### 3.2.3 截图策略优先级

| 条件                       | 使用方案              | 预期延迟       |
| ------------------------ | ----------------- | ---------- |
| DXGI 后台线程运行中             | 共享缓冲区 numpy slice | ~0.1-0.5ms |
| DXGI 未启动 + 区域 < 500x500  | BitBlt 局部截图       | ~2-8ms     |
| DXGI 未启动 + 区域 >= 500x500 | mss 全屏/区域截图       | ~15-40ms   |

#### 3.2.4 与 ExecContext 集成

- `ExecContext` 新增属性 `_capture_manager: CaptureManager | None`
- `execute_graph` 结束时的 `finally` 块中，调用 `ctx._capture_manager.stop_dxgi()` 确保资源释放

### 3.4 改造：颜色检测模块 (`automation/detection/color.py`)

#### 3.4.1 新增 `area` 检测模式

**算法**：使用 `cv2.inRange`（底层 SIMD 优化）替代 `np.linalg.norm`

```python
if mode == "area":
    b, g, r = target
    lower = np.array([max(0, b-tol), max(0, g-tol), max(0, r-tol)], dtype=np.uint8)
    upper = np.array([min(255, b+tol), min(255, g+tol), min(255, r+tol)], dtype=np.uint8)
    mask = cv2.inRange(image, lower, upper)  # SIMD 加速
    matching = cv2.countNonZero(mask)
    ratio = matching / (image.shape[0] * image.shape[1])
    found = ratio >= area_ratio_threshold
```

#### 3.4.2 `check_color` 函数签名更新

```python

                last_image=None, change_threshold=10,
                area_ratio_threshold=0.5):  # 新增参数
```

#### 3.4.3 返回值

- `mode="area"` 时：`actual_color` 返回目标颜色的 hex（因为检测的是"某颜色是否出现"）

### 3.5 新增模块：模板图像缓存 (`automation/detection/image_cache.py`)

#### 3.5.1 设计目标

避免每次模板匹配都从硬盘读取图片，通过内存缓存 + 文件修改时间校验确保数据新鲜。

#### 3.5.2 实现

```python
import cv2
import os

_template_cache = {}   # path -> np.ndarray
_mtime_cache = {}      # path -> float (mtime)

def load_template(path: str) -> np.ndarray | None:
    if not path:
        return None
    abs_path = os.path.abspath(path)
    try:
        current_mtime = os.path.getmtime(abs_path)
    except OSError:
        return _template_cache.get(abs_path)
  
    cached = _template_cache.get(abs_path)
    if cached is not None and _mtime_cache.get(abs_path) == current_mtime:
        return cached
  
    img = cv2.imread(abs_path, cv2.IMREAD_COLOR)
    if img is not None:
        _template_cache[abs_path] = img
        _mtime_cache[abs_path] = current_mtime
    return img

def clear_cache():
    _template_cache.clear()
    _mtime_cache.clear()
```

#### 3.5.3 使用位置

- `_handle_check_image` 中替换 `cv2.imread(template_path, cv2.IMREAD_COLOR)`

### 3.6 改造：图像匹配处理器 — 图像金字塔优化

#### 3.6.1 自动启用条件

当同时满足：

- 搜索区域面积 > 500x500（即 25万像素）
- 模板图片面积 > 50x50（即 2500像素）

#### 3.6.2 算法流程

```
match_template_pyramid(img, template, threshold, method, max_levels=2)
├── 构建金字塔：对 img 和 template 各做 max_levels 次 pyrDown
├── 在最小金字塔层执行 cv2.matchTemplate
├── 如果无匹配 → 返回 found=False
├── 取最佳匹配位置，映射回原图坐标
├── 在原图对应 ROI 区域执行精确 matchTemplate
└── 返回最终结果 + 置信度 + 坐标
```

#### 3.6.3 性能预期

- 2层金字塔可将搜索区域缩小到 1/16，模板缩小到 1/16
- `matchTemplate` 计算量与 (W-w+1)*(H-h+1) 成正比，金字塔后约为原图的 1/256
- 大区域匹配从 ~200ms 降至 ~20-40ms

### 3.8 改造：检测节点 — 增加"等待/轮询"能力

#### 3.8.1 通用新增参数（适用于所有检测节点）

在 `detection/check_color`、`detection/check_ocr`、`detection/check_image`、`detection/check_screen` 的 `params_schema` 中统一新增：

```python
"wait": {
    "type": "boolean",
    "default": False,
    "description": "是否持续检测直到条件满足或超时。开启后节点会阻塞并轮询检测"
},
"wait_interval_ms": {
    "type": "number",
    "default": 16,
    "minimum": 1,
    "maximum": 5000,
    "description": "轮询间隔(ms)，建议 16ms(60FPS) 或 33ms(30FPS)"
},
"wait_timeout_ms": {
    "type": "number",
    "default": 5000,
    "minimum": 0,
    "description": "等待超时(ms)，0=无限等待"
}
```

#### 3.8.2 执行逻辑改造（以 check\_color 为例）

```python
def _handle_check_color(node, ctx):
    params = node.params
    wait = params.get("wait", False)
    interval_ms = params.get("wait_interval_ms", 16)
    timeout_ms = params.get("wait_timeout_ms", 5000)
  
    def _do_check():
        # ... 原有单次检测逻辑 ...
        return result
  
    if not wait:
        # 单次检测模式（完全兼容现有行为）
        result = _do_check()
        _execute_flow(node.id, "match" if result["found"] else "no", ctx)
        return
  
    # 持续检测模式
    start_time = time.perf_counter()
    while not ctx.stop_event.is_set():
        result = _do_check()
    
        if result["found"]:
            # 条件满足 → match 端口
            ctx.check_results[f"{node.id}.result"] = True
            ctx.check_results[f"{node.id}.color"] = result.get("actual_color", "")
            _execute_flow(node.id, "match", ctx)
            return
    
        # 检查超时
        if timeout_ms > 0 and (time.perf_counter() - start_time) * 1000 > timeout_ms:
            ctx.check_results[f"{node.id}.result"] = False
            ctx.check_results[f"{node.id}.color"] = ""
            _execute_flow(node.id, "no", ctx)  # 超时走 no 端口
            return
    
        # 等待下一轮
        precise_sleep(interval_ms / 1000.0, ctx.stop_event)
  
    # 被外部终止
    ctx.check_results[f"{node.id}.result"] = False
    ctx.check_results[f"{node.id}.color"] = ""
    _execute_flow(node.id, "no", ctx)
```

#### 3.8.3 端口行为

| 模式                  | match 端口触发条件 | no 端口触发条件         |
| ------------------- | ------------ | ----------------- |
| 单次检测 (`wait=False`) | 单次检测满足       | 单次检测不满足           |
| 持续检测 (`wait=True`)  | 轮询中某次满足      | 超时仍未满足 或 被外部 stop |

**不新增** **`timeout`** **端口**，超时统一走 `no` 端口，保持向后兼容。

## 5. 用户使用场景示例

### 场景 1：快速检测某按钮颜色（使用 DXGI + 等待）

```
[开始] → [截图源 enabled=True fps=60] → [颜色检测 wait=True wait_timeout_ms=3000]
                                            ├──match──→ [点击按钮] → [截图源 enabled=False] → [结束]
                                            └──no────→ [处理超时]
```

**延迟预期**：颜色检测轮询间隔 16ms，每次检测 \~0.3ms，从按钮出现到检测到约 16-32ms。

### 场景 2：模板匹配（大区域搜索）

```
[开始] → [图像匹配 rect=[0,0,1920,1080] template="btn.png" wait=True wait_timeout_ms=10000]
            ├──match──→ [点击匹配位置] → [结束]
            └──no────→ [报错]
```

**延迟预期**：使用图像金字塔，大区域匹配从 \~200ms 降至 \~30ms。

### 场景 3：未使用截图源（自动 fallback）

```
[开始] → [颜色检测 rect=[100,100,50,50]] ──match──→ [继续]
            └──no────→ [结束]
```

**延迟预期**：DXGI 未启动，自动使用 BitBlt 局部截图，\~3-8ms。

## 6. 风险与回退策略

| 风险                      | 影响         | 回退策略                                            |
| ----------------------- | ---------- | ----------------------------------------------- |
| DXGI 初始化失败（驱动不支持、远程桌面）  | 后台截图无法启动   | 自动 fallback 到 BitBlt/mss，用户无感知                  |
| DXGI 帧获取超时（GPU 忙、显示器休眠） | 获取不到最新帧    | 返回上次缓存帧，超时 3 次后尝试重新初始化                          |
| 多显示器配置复杂                | 可能获取到错误显示器 | 默认使用主显示器（adapter\_idx=0, output\_idx=0），后续可扩展参数 |
| 内存占用增加                  | 共享帧缓冲常驻内存  | 全屏 BGRA 1920x1080 约 8MB，可接受                     |
| 模板缓存不刷新                 | 文件修改后仍用旧图  | image\_cache 已加入 mtime 校验，修改后自动重新加载             |

## 8. 待确认事项

1. **DXGI 多显示器支持**：是否需要在 `capture_source` 节点中增加 `monitor_index` 参数？ A：不做成参数，默认截全屏，因为多个不同的OCR任务可能需要从不同的显示器截取不同的区域。
2. **BitBlt 窗口模式**：当前 BitBlt 实现是否支持截取指定窗口（而不仅是屏幕坐标）？   A：不用，OCR节点传入的参数已经根据具体窗口或相对位置调整了具体坐标。
3. **图像金字塔层数**：固定 2 层，还是作为 `check_image` 的可配置参数？  A：要可配置参数
4. **检测节点 wait 模式的 UI 提示**：前端是否需要对 `wait=True` 的节点做特殊视觉标识（如显示"⏳等待中"）？  A：目前所有正在执行的节点在要外圈添加简单的细微波浪特殊动效
